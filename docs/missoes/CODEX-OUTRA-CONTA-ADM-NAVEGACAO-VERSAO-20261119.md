## PROBLEMA REAL #1 — DOIS LINKS / PAINEL ADM DESCONECTADO
O criador relata: há um link “normal” e outro com opções ADM; no modo ADM, ao clicar em enfrentar inimigo, viajar para área ou usar tela cheia, é redirecionado para outra página/link, perde a interface ou a lógica de ADM; a experiência é confusa.

Constatação feita na main: `index.html` injeta iframe `mundo-3d-prototype.html`, mas não encaminha todos os parâmetros de teste; `laboratorio-inimigos.html` carrega outra instância da mesma página no iframe e usa `target="_blank"` no link `Tela cheia`, que abre **nova guia**, NÃO solicita `requestFullscreen()`. Além disso, no método `travel`, opções de dimensão definem `testeDimensao` mas **não** `adm`/`debug3d`; já a jornada define `adm=1`/`debug3d=1`, produzindo experiências diferentes. Conferir intenção do usuário e preservar o modo de teste.
**Resultado:** um ponto de entrada principal coerente, o painel/ferramentas de teste acessíveis somente quando solicitados, trocas de destino dentro da interface atual sem abrir nova guia/destruir shell, e tela cheia **REAL** via Fullscreen API no elemento do jogo/container, preservando o painel ADM e oferecendo saída. Se Fullscreen API não for suportada/negada, alternativa honesta e claramente identificada; nunca chamar de fullscreen um link target=_blank.

Implementação sugerida:
- Definir uma função central para serializar/encaminhar parâmetros de navegação (adm, debug3d, testeDimensao, jornadaInicio, build, entre outros necessários); evitar cair em URL que apaga estado ADM. Não duplicar app nem criar 2 motores em execução.
- Distinguir seleção de missão/teleporte em runtime (se API existente suportar) de recarregar iframe intencionalmente; preservar saves e retorno à UI. Se for inevitável recarregar ao trocar dimensão, manter o shell ADM e indicar recarga de forma curta.
- Compatibilidade com `?adm=1&debug3d=1`, link normal, atalhos existentes de “TESTAR”, TP para vulcão, mobile Android e desktop; não deixar novos botões encobrirem joystick/HUD.
- Incluir smoke browser test para abrir shell normal, entrar laboratório, trocar Bispo 1→Bispo 2→jornada→Bispo 4, usar fullscreen/esc e confirmar que a interface permanece na mesma aba e parâmetros ADM preservados. Não alegar prova sem executar.

## ETAPA 2 — AUDITORIA E CORREÇÃO DA EXPERIÊNCIA EM PC / NAVEGADOR DESKTOP / EMULADOR
**Relato do criador:** em um PC da escola, durante o jogo, **algumas teclas paravam de funcionar subitamente**. Foi uma observação esporádica, e ele não determinou causa nem testou o sistema inteiro. O usuário falou “emulador”; **priorize o jogo web rodando em navegadores no PC**, e inclua emuladores de Android apenas se houver ambiente de teste representativo, sem prometer universalidade.

**Auditoria sistemática de entrada e jogabilidade:**
- Reproduzir e instrumentar eventos `keydown`, `keyup`, `blur`, `focus`, `visibilitychange`, `pointerlockchange`, `fullscreenchange`, foco em `iframe`, mudanças de rota/painel ADM e contexto de menu/chat. Verificar captura por formulários, `preventDefault`, `event.repeat`, composição de input, teclas presas depois de alt-tab, reentrada na aba, fullscreen/Esc e recargas de iframe.
- Investigar estados de teclas que ficam permanentemente presas ou deixam de ser lidas, diferentes layouts ABNT2/US (WASD, setas, espaço, Shift, E, Esc e atalhos usados no jogo), simultaneidade de várias teclas, rollover/ghosting físico em teclado de escola, perda de pointer lock e gamepad conectado. Registrar evidência que separa bug de software de limitação do hardware. Nunca tornar `preventDefault` global para tudo, prejudicando navegação/atalhos do navegador.
- Testar jornada desde spawn, caminhar/correr/pular/dash, câmera/mouse, interagir com NPC/objeto, abrir/fechar menus, inventário/loja/ADM, teleporte, áreas distintas, combate básico **somente como teste de regressão** (não alterar o combate) e retorno de foco após fechar menus; conferir os atalhos reais do projeto em vez de supor que E/Shift fazem uma ação específica.
- Investigar problemas próprios da experiência desktop: sensibilidade e invertida mouse, aceleração indesejada, travamento com mouse, pointer lock confiável, reset de foco, resolução/aspect ratio, pixel ratio/FPS, webgl context loss/recovery, resize, fullscreen, teclado simultâneo, visibilidade de HUD móvel no PC, latência de entrada, lag/microtravadas e acessibilidade mínima. **Não redesenhar controles nem reescrever câmera em conflito com Claude**. Melhorias devem ser cirúrgicas, compatíveis com celular, respeitando preferências de configuração.
- Compatibilidade: Chrome/Edge desktop como prioridade, Firefox quando viável; desktop com teclado/mouse e emulação de viewport mobile. Se houver emulador Android disponível, validar ali sem alegar que representa celular real. Rodar um ciclo curto de 10–15 minutos de gameplay contínuo automatizado + entradas rápidas/alternadas; se isso não for viável, registrar limitação concreta, não inventar QA.
- **Aceite:** provar antes/depois a falha encontrada, validar teclado depois de alt-tab/menus/fullscreen/iframe/TP, e não causar regressão no celular. Nenhum bug residual de entrada silenciosamente ignorado; listar o que ficou bloqueado.
